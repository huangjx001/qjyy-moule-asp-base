# 详细设计文档（定义态建模服务）

## 背景与目标

该系统面向制药/离散制造场景，提供“工艺路线定义态”的建模能力，用于把“工序-资源-工步-设备-依赖约束”结构化沉淀为可计算数据，并为后续 Timefold 排产提供可靠底座。

## 1. 目标与范围

该服务负责“工艺路线定义态”的完整建模：路线/版本、工序 DAG、资源（房间）、工步 DAG、设备挂载与汇总，并预留运行态扩展能力。工序/工步/资源的主数据由基础数据表统一沉淀，定义态在版本中引用并保留快照字段。

## 2. 后端设计整体思路（从“画布”到“可执行”）

### 2.1 路线与版本

- 路线：按产品/剂型维护。
- 版本：`DRAFT/RELEASED/OBSOLETE`，发布前必须校验通过。

### 2.2 领域建模主线：定义态 vs 运行态

- **定义态（工艺路线建模）**：核心产物。
  - 工序 DAG（节点 + 边）。
  - 工序下资源（房间/资源实例）。
  - 资源下工步 DAG（节点 + 边）。
  - 资源/工步设备挂载（含来源追溯）。
- **运行态（排产/执行）**：未来对接排产引擎时，把定义态实例化为。
  - 订单/批次 → 一组具体任务（工序任务/工步任务） → 分配到资源/设备并排时间。

### 2.3 工序/工步/资源基础数据

- **工序基础数据**：统一维护工序编码、名称、类型、默认时长、关键工序标识。
- **工步基础数据**：统一维护工步编码、名称、类型、默认时长、QC 点标识。
- **资源基础数据**：统一维护资源编码、名称、类型、能力描述、默认清场时间。
- **引用策略**：定义态节点/资源记录基础数据 ID，同时保留 `code/name/type` 等快照字段，避免基础数据变更影响已发布版本。

### 2.4 工序画布（一级图）

- 节点：工序属性与坐标。
- 边：依赖类型（FS/SS/FF/SF）、硬/软、时滞。
- 校验：无环、节点存在、边引用合法。

### 2.5 工序下资源（房间）

- 每个工序维护多个房间资源。
- 资源属性：优先级、清场/换线时间。

> 设计原则：定义态数据结构保持“干净、可扩展”，以便运行态实例化时不需要推倒重来。

### 2.6 资源下工步画布（二级图）

- 工步节点：时长、QC 点、坐标。
- 工步边：依赖类型、硬/软、时滞。
- 校验：无环、引用合法、关键设备完整性。

### 2.7 设备挂载与汇总

- 资源级设备挂载。
- 工步级设备挂载。
- 汇总：资源页返回设备 + 来源（RESOURCE/STEP）+ 来源工步名。

### 2.8 双层图的数据存储与校验策略

- **存储**：采用“节点表 + 边表”的结构化存储（避免一坨 JSON）。
  - 易查询（统计工序下资源数/工步数）。
  - 易校验（无环、边引用合法）。
  - 易增量保存（拖拽仅更新坐标、改边只更新边）。
- **校验**：服务层实现 DAG 校验与业务规则校验。
  - 工序图：无环、孤立节点、边引用同版本节点、必填配置（如必须有资源）。
  - 工步图：无环、边引用同工序/同资源范围、必填配置（如工步必须挂设备）。

## 3. 数据模型概要

参考数据库设计文档，核心实体如下：

- `process_route` / `process_route_version`
- `process_base` / `resource_base` / `step_base`
- `process_node` / `process_edge`
- `resource_room`
- `step_node` / `step_edge`
- `device` / `device_mount`

后端提供汇总字段，前端只渲染：

- **工序摘要**：资源数 R、工步数 S（资源下汇总）、设备数 E（资源级 + 工步级去重）。
- **资源设备汇总**：设备 + 来源类型（RESOURCE/STEP）+ 来源工步名。

## 4. 服务层校验策略

### 4.1 DAG 校验

- **Graph**：get/save/validate（工序图、工步图）。
- **配置**：资源列表、资源设备、工步设备。
- **汇总**：工序摘要、资源设备汇总（含来源）。

### 4.2 业务规则校验

- 工序必须至少有一个资源。
- 关键工步必须挂设备。
- `RELEASED` 版本不可编辑。

## 5. 版本化与发布：编辑版 vs 发布版

- 路线版本状态：`DRAFT / RELEASED / OBSOLETE`。
- `DRAFT`：可编辑（画布拖拽、增删改）。
- `RELEASED`：冻结（不允许改或走变更流程）。
- 发布动作：强制 validate，全部通过才允许发布。

## 6. 业务范围与系统目标

### 6.1 系统定位

制药离散制造的“工艺路线建模 + 产能约束建模 +（后续）智能排产”的基础平台，连接工艺人员、计划人员、车间资源，将“经验流程”沉淀为“可计算、可校验、可优化”的结构化数据。

### 6.2 解决的问题

- 工艺路线/工步依赖关系复杂，靠 Excel/口头传递容易错、难复用。
- 资源（房间）限制、设备限制分散在经验中，缺少统一建模与校验。
- 缺少标准化的“可用于排产引擎”的数据底座。
- 需要在 UI 上直观看到流程、依赖、缺项，并能快速定位修正。

## 7. 核心功能清单（模块划分）

### 7.1 路线与版本管理

- 路线：按产品/剂型维护路线。
- 版本：新建/复制/发布/作废。
- 变更记录：版本差异、原因。

### 7.2 工序画布（一级画布）

- 工序节点：新增/拖拽/属性编辑（时长、类型、可选等）。
- 工序依赖边：FS/SS/FF/SF + lag + 硬/软。
- 校验：无环/孤立/边合法/必填项提示。
- 摘要：节点显示 R/S/E + 状态。

### 7.3 工序内资源（房间）管理

- 在工序内维护资源列表（房间 A/房间 B…）。
- 优先级、`setup_time`（清场/换线准备）。
- 资源状态（是否满足配置）。

### 7.4 资源内工步画布（二级画布）

- 工步节点：只能在资源下创建。
- 工步依赖边：FS/SS/FF/SF + lag + 硬/软。
- 工步属性：时长、QC 点、可选。
- 校验：无环、依赖合法、设备缺失提示。

### 7.5 设备挂载与设备汇总

- 资源挂设备（资源级）。
- 工步挂设备（工步级）。
- 资源页设备汇总：合并展示两类设备，并标明来源工步（可定位回工步）。

### 7.6 （后续）排产与结果展示

- 输入：订单/批次、时间窗口、资源日历。
- 输出：任务排程（开始/结束、分配资源/设备）。
- 前端展示：资源甘特图、冲突提示、调整建议。

### 7.7 日志/审计/通知

- 操作审计：谁改了路线、改了什么。
- 校验/发布日志。
- 通知：发布、校验失败、变更提醒（可走 Kafka）。

## 8. 角色与权限（RBAC 建议）

### 8.1 典型角色

- 系统管理员：用户/角色/权限、基础字典、全局配置。
- 工艺工程师：维护路线、工序/工步、依赖关系；配置资源与设备挂载；发起发布。
- 计划员/排产员：选择订单/时间窗口执行排产；调整参数；查看/导出结果。
- 车间主管/班组长：查看发布版本、查看资源负载与计划。
- 设备管理员（可选）：维护设备主数据、设备状态、设备移动/归属房间。

### 8.2 权限颗粒度建议

- 路线：查看/编辑/发布/作废。
- 图编辑：节点/边增删改。
- 资源/设备挂载：编辑权限单独拆分。
- 排产：执行/查看/导出/参数调整。

## 9. 数据需求

### 9.1 建模核心数据（定义态）

- 路线、版本。
- 工序节点（含坐标）、工序依赖边。
- 工序下资源实例（房间绑定、优先级、`setup_time`）。
- 资源下工步节点（含坐标）、工步依赖边。
- 资源级设备挂载、工步级设备挂载。
- 汇总视图（实时聚合或缓存表/物化视图）。

### 9.2 主数据（基础）

- 资源/房间主数据（类型、能力、日历）。
- 设备主数据（类型、是否可移动、当前位置/归属）。
- 字典：`depType`、`uom`、节点类型、状态等。

### 9.3 历史/日志/附件

- 操作审计日志（差异、操作者、时间）。
- 发布日志/校验结果快照。
- 附件：工艺文件/作业指导书（可选）。

## 10. 接口需求

### 10.1 内部 API（前端/服务调用）

- 路线/版本 CRUD、发布。
- 工序图 get/save/validate。
- 工序资源列表 CRUD。
- 资源工步图 get/save/validate。
- 设备挂载 CRUD（只需设备编号，详情由设备系统微服务提供）。
- 资源设备汇总（含来源工步）。
- 工序摘要接口（R/S/E 与状态）。

### 10.2 外部/第三方对接（建议）

- 产品主数据/物料：ERP/主数据平台。
- 生产订单/批次：MES/ERP。
- 设备/房间状态：设备管理系统或 MES。
- 通知总线：Kafka。

## 11. 技术栈偏好（结合现状）

### 11.1 后端

- Java 8 + Spring Boot。
- MyBatis-Plus / MyBatis。
- MySQL。
- DAG 校验：服务层实现拓扑排序/DFS。

### 11.2 前端

- Vue 3。
- LogicFlow（工序画布/工步画布复用同一套渲染与交互）。
- Element Plus 或 Ant Design Vue。

### 11.3 排产（后续）

- Timefold（定义态实例化为任务后求解）。

### 11.4 消息与集成

- Kafka（变更通知、发布事件、排产任务状态）。

## 12. 非功能要求

### 12.1 性能与并发

- 画布保存高频：坐标保存做增量更新；边更新做 upsert + 批量。
- 图查询优化：节点/边按版本/工序建立索引。
- 摘要 R/S/E 可做聚合缓存（发布后固化）。

### 12.2 事务与一致性

- “保存图”建议事务包裹：更新节点坐标、更新边、更新资源/工步。
- 发布操作：validate + 状态切换事务化。

### 12.3 部署环境

- Docker/K8s。
- 分层：建模服务、排产服务可拆分。

### 12.4 安全与合规

- RBAC 权限控制。
- 审计追踪（谁在何时改了什么）。
- 关键操作（发布/作废）支持二次确认或电子签名（如需合规）。

## 13. DAG 校验策略（算法视角）

- 入参：节点列表、边列表。
- 校验：
  - 节点 ID 唯一且非空。
  - 边引用节点必须存在。
  - Kahn 拓扑排序检测无环。

## 14. API 设计（示例）

### 14.1 工序图校验

`POST /api/graphs/process/validate`

请求体：

```json
{
  "routeVersionId": "rv-1001",
  "nodes": [
    {"id": "p1", "name": "混合", "type": "MIX", "durationMinutes": 60, "x": 100, "y": 120}
  ],
  "edges": []
}
```

响应体：

```json
{
  "valid": true,
  "errors": []
}
```

### 14.2 工步图校验

`POST /api/graphs/step/validate`

请求体：

```json
{
  "resourceRoomId": "r-1001",
  "nodes": [
    {"id": "s1", "resourceRoomId": "r-1001", "name": "清场", "type": "CLEAN", "durationMinutes": 30, "qcPoint": false, "x": 80, "y": 140}
  ],
  "edges": []

```

## 15. 聚合接口建议

- 工序摘要：`GET /api/routes/{routeVersionId}/process-summary`。
  - 返回每个工序节点的 R/S/E 统计与状态。
- 资源设备汇总：`GET /api/resources/{resourceRoomId}/devices`。
  - 返回设备列表，标注来源类型与来源工步。

## 16. 版本发布流程

1. 触发发布：`POST /api/routes/{routeVersionId}/release`。
2. 服务端执行完整校验（图/资源/设备）。
3. 全部通过后状态切换为 `RELEASED`，并写入发布日志。

## 17. 运行态扩展预留

- 运行态任务表与定义态表通过 `route_version_id` 关联。
- 运行态任务由排产引擎生成：工序任务/工步任务 + 分配资源/设备 + 时间窗口。

## 18. 代码落位说明

- `GraphValidationService`：DAG 校验与引用合法性校验。
- `GraphController`：提供图校验接口供前端画布保存前调用。
- DTO 采用不可变 record，便于序列化与校验。

## 19. 实现约束与规范（对齐现有代码仓）

### 19.1 数据库建表与注释

- 建表语句统一维护在 `docs/schema.sql`，包含完整中文注释与视图定义。
- 表字段、索引、视图需与“定义态建模”一致，避免运行态强耦合。

### 19.2 日志与注释语言

- 业务日志统一中文输出，便于一线排查。
- 关键逻辑、枚举、DTO 字段等使用中文注释，确保交付可读性。

### 19.3 Lombok 与转换器规范

- 实体/DTO 使用 Lombok 注解简化样板代码（如 `@Data`、`@Builder`、`@NoArgsConstructor`、`@AllArgsConstructor`）。
- 类型转换采用 MapStruct，统一放在 `convert` 包。

```java
@Mapper(
    componentModel = "spring",
    unmappedTargetPolicy = ReportingPolicy.IGNORE,
    nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE
)
public interface BaseConvert {
}
```

### 19.4 MyBatis 查询落位

- 简单查询优先使用 MyBatis-Plus API（Wrapper 等）。
- 复杂查询使用 XML，统一放置在 `resources/mapper` 下，便于维护与审查。

### 19.5 目录结构与风格对齐

- 代码组织对齐现有包结构：`com.example.route` 下保持 `controller/service/mapper/entity/dto/vo/domain/common` 等目录风格。
- 新增代码需参考现有类命名与注解风格（如 MyBatis-Plus 与 Swagger 注解），避免出现与仓内风格不一致的实现方式。
